## 성능 개선 전 코드 확인

- `goFileSystem.OpenFile`은 `stat`을 먼저 호출한다.
- `goFileSystem.stat`은 동일 경로의 dirty 파일을 반영한 후 backend `Stat`을 호출한다.
- WebDAV `Stat`은 `PROPFIND Depth: 0`, `ReadDir`은 `Depth: 1`을 호출한다.
- `ReadDir`의 자식 메타데이터를 이후 경로별 `Stat`이 공유하는 캐시는 없다.
- 연결별 메타데이터 캐시와 공통 호출 계측은 아직 없다.

이는 요청 중복 가설을 뒷받침하지만 실제 지연의 원인을 확정한 측정 결과는 아니다.
HTTP Transport 변경은 메타데이터 최적화 뒤에도 요청 자체가 병목이라는 근거가
있을 때만 검토한다.

## 단계별 실행 계획

1. **Phase 1:** 기준 문서 정합성 수정, 기준 빌드·검증, PR 및 CI 확인.
2. **Phase 2:** 제한된 진단 모드에서 논리 Stat/ReadDir 횟수·시간과 실제
   WebDAV Depth 0/1, FTP/FTPS 목록·메타데이터, SFTP Stat/ReadDir 요청 계측.
   counting backend 탐색 패턴 자동 테스트 및 한 번에 실행할 Windows 기준 측정 절차 제공.
3. **Phase 3–5:** 측정 결과가 가설과 일치하면 연결별 `vfs.Backend` 캐시 구현.
   초기 TTL 후보는 Stat/ReadDir 2초, 명확한 NotFound 500ms.
   경로 정규화·대소문자 유지·slice 복사·상한·만료·종료 정리와 자식 Stat 연계를 포함한다.
   인증·권한·timeout·취소·단절·서버 오류는 음수 캐시하지 않는다.
   생성·삭제·이동·속성 변경 및 쓰기 Sync/Close·부분 반영 가능한 실패에서 무효화한다.
4. **Phase 6:** 동일 Stat/ReadDir 동시 요청 병합. 다른 경로 병렬성, 실패 정리,
   대기 호출 취소 독립성 검증. 새 외부 의존성은 필요성 보고 후 추가한다.
5. **Phase 7:** 같은 폴더의 변경 전후 WebDAV·FTPS·SFTP 검증. 20/100/500개 이상
   폴더의 최초·재방문·하위 이동·뒤로 이동 시간과 호출 수를 기록한다.
   썸네일·미리보기 사용을 기록하고 RaiDrive는 참고 비교만 한다.
6. **Phase 8–9:** 로그인·종료·프로토콜 장애·읽기 전용 부정 동작 검증.
   남은 요청 지연에 근거가 있을 때만 HTTP 연결 재사용 설정 검토.
7. **Phase 10:** EXE 리소스, 단일 버전 기준, 재현 가능한 Windows GUI 빌드,
   ZIP·SHA-256·설치·복구·제거·제한사항 문서 작성.
8. **Phase 11:** formatting·module 정합성·전체 테스트·VFS race·vet·Windows GUI 빌드·CI,
   Windows 릴리스 후보 회귀 및 새 폴더에 배포 ZIP을 풀어 실행 검증.

각 단계는 작은 커밋, 자동 검증, 문서 갱신, PR, CI 확인 및 남은 수동 항목 보고로
진행한다. 성능 개선은 자동 테스트만으로 완료 처리하지 않는다.

## 실환경 및 사용자 결정이 필요한 사항

- Windows 로그인 후 한 번만 자동 실행·자동 연결되는지 확인.
- 종료·재시작을 막지 않는지, 열린 쓰기 파일이 있을 때 보존·종료 지연 확인.
- FTP/FTPS·SFTP의 장시간 및 전송 중 단절, WebDAV 불확실한 쓰기의 보존 확인.
- 읽기 전용에서 기존 파일 덮어쓰기·이름 변경·파일 및 폴더 삭제 차단과 읽기 유지.
- Implicit FTPS 실제 서버가 필요하다. 현재 GUI는 이미 실서버 미검증으로 표시한다.
  지원 제거 또는 실험 기능으로 변경하려면 사용자 확인을 받는다.
- 최종 버전, 회사명 등 미확정 제품 정보는 해당 단계에서 확인한다.
  사용자 승인 없이 tag 또는 공개 Release를 생성하지 않는다.

설치 관리자·서명·자동 업데이트·설정 호환성 변경·추가 GUI 설정은 확정 범위가 아니다.
수동 검증은 각 단계에서 한 번에 실행할 절차로 묶고, 확인할 수 없는 항목은 이유를
기록한다. 릴리스 후보는 성능 비교, 데이터 보존, 잔여 실환경 결과와 배포 산출물이
모두 확인되거나 사용자가 승인한 지원 범위로 정리된 뒤에만 완료한다.
